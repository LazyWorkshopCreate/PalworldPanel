# 文档维护规则

日期：2026-10-05。状态：现行规则。适用于仓库文档和 Markdown 说明；用户当前指示优先，AGENTS.md 的项目边界继续适用。

## 内容归属与权威来源

需求只写目标、范围、流程和可验收行为；设计写如何实现和失败处理；计划写工作项、依赖、交付物与验收条件，不写工时、人员或交接安排。调研记录来源与比较，ADR 记录选择及取舍，验证记录只写已经取得的证据和真实限制。

业务行为以 requirements 为准，技术契约以 design 为准，工程数值初值以 operational-defaults 为准；ADR 是决策依据，计划负责执行追踪。docs/README.md 只做导航和摘要，不复制完整规则。发现冲突先修订相关现行文档；不能用“某文件优先”隐藏矛盾。用户已确定的约束无需重复确认。

## 格式与命名

- 正文中文，路径/标识符使用英文，文件名使用小写连字符；保留既有固定入口和 REQ/W/ADR 编号。
- 官网公开内容按用户要求维护中英双语；英文发行说明位于 `docs/releases/en/`，与中文说明同名同版本，按相同日期和归档规则维护。内部需求、设计、计划与验证继续使用中文。
- 新方案注明日期、状态、适用范围；快照注明采集时间和非实时性质；资料注明核对日期和原始链接。
- Markdown 使用相对仓库链接，目录迁移同步所有引用。章节深链接变更需人工核对；程序目前只检查文件目标存在。
- 标题层级从一个一级标题开始；表格及列表前留空行，围栏注明语言；文档 UTF-8 无 BOM、LF 换行；Windows PowerShell 5.1 部署源码的 BOM 例外见工程规则。
- 示例只用占位符、合成数据或明确脱敏内容；不粘贴未筛选日志、全量环境变量、真实存档和秘密。

## 变更与状态

每个主题维护一份现行版本，Git 保留修订历史，仓库归档保留被实质替代的完整版本。原始任务书/快照不重写历史事实；新证据另建日期记录，导航标清哪个记录适用。具体命名及替代流程见下节。

## 日期前缀与归档

需求、调研、技术设计、运维策略、实现计划、验证记录、环境快照、任务书和依赖具体版本的运维手册均使用 `YYYY-MM-DD-主题.md`，日期按北京时间取该版本建立或核对日。必须是有效年月日，不使用仅年份/月或泛称 latest；日期不代表结论自动有效，也不把未经复核的材料改成今天日期。当前版本以导航明确指向为准，不按文件名大小自动选择。

README、AGENTS、CONTRIBUTING、standards 中长期维护规则及 templates 不要求日期文件前缀。ADR 按递增编号和状态维护，正文仍注明日期，不因编号代表决策仍适用。`docs/current-environment.md` 和 `docs/research-brief.md` 只保留稳定索引，事实正文位于带日期的 context 文件。

排版、纠错、链接修复及不改变适用范围的补充直接修改现行文件，保留版本前缀，正文可记录修订日期。需求范围、核心架构、策略或阶段计划实质变更，以及新的环境复核取代旧快照时，建立新日期版本；同日实质替代用 `YYYY-MM-DD-主题-r2.md` 递增。REQ、W 等身份编号跨版本保留，不因日期重排。

替代流程：先建立并检查新版本 → 移动旧版至 `docs/archive/<归档发生日>/<原分类>/<原日期文件名>` → 修复迁移链接 → 在[归档台账](../archive/README.md)登记原版本日期、归档日期、原因和替代链接 → 新版注明替代来源 → 更新导航、两个固定入口及相关引用 → 运行文档检查。文件移动前验证目标不存在；禁止覆盖同日旧版。只因本次补日期而迁移的现行文件无需归档。

归档正文冻结，不继续更新业务内容；仅允许修复失效链接并说明修复。没有替代者时台账标撤销/终止及原因，不能自动复活为现行。已结束的验证记录可归档，但保留实际结果和当时范围；仍作为当前验收依据的证据留在 verification。归档默认长期保留，不自动按时间删除；清理历史须用户明确要求，秘密和真实存档始终不得纳入任何归档。

文件被替代后，现行文档不能依赖归档中的过期约束；历史比较、替代来源及证据引用应显式标为历史。跨主题更新需求、设计、计划与决策状态，不能只修改导航。新版本记录“版本日期、修订日期、状态、适用范围、替代来源”，无替代写“无”。可参考[时效文档模板](../templates/dated-document.md)。

ADR 使用递增三位编号，编号不复用。状态为拟议、已采纳、已替代或已撤销；保留背景、决策、备选、后果与验证边界。已采纳 ADR 的排版、链接和补充证据可直接修订；实质改选新增 ADR，旧记录注明由哪个编号替代。

计划/验证采用 Not Run、Passed、Failed、Blocked，Blocked 必须说明具体缺失输入或证据。设计已确定、文档检查 Passed、工程 Not Run 可以同时成立。不可把 API 健康、容器启动、文档链接通过等同于真实玩家恢复或生产可用。

## 最小检查清单

1. 更新相关 REQ、设计、W 工作项、ADR 和导航，保证端口、状态、默认值和范围一致。
2. 运行 `pwsh -NoProfile -File scripts/Test-Documentation.ps1` 和 `git diff --check`，确认迁移后旧路径没有意外引用。
3. 人工检查标题锚点、Mermaid 语义、表格、敏感资料和已验证/未验证表述；外部链接需要按具体研究任务核实，文档脚本不访问网络。
4. 记录检查日期、命令、结果、未覆盖项；本地脚本通过不自动把计划改为 Passed。

可用模板见 [ADR](../templates/adr.md) 和[验证记录](../templates/verification-record.md)。小修改无需创建额外报告或重复审批。

## 本项目规范表达

技术栈和 UI 风格须描述为 PalworldPanel 自己的设计契约，分别维护在导航选定的 technology-stack 与 ui-style 日期文档中。业务文档不依赖其他项目的名称、源码路径、提交哈希、配置声明或产品策略来定义本项目行为。公开官方资料仍可用作技术事实来源；外部产品选型比较仅保留本项目调研所需内容，不替代现行规范。

用户明确要求清理范围外来源或敏感材料时，可以修订现行文档、原任务书/快照中的相关内容并记录清理范围，不生成仍含被要求移除内容的归档副本；保留相关实例事实与尚未验证的边界。此类清理不视为架构改选，也不虚构新的工程验证。
